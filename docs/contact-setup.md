# Приём заявок

## Что реализовано

Статический сайт отправляет JSON на `/api/contact`. Это Cloudflare Pages Function `functions/api/contact.js`, без платного внешнего сервиса и новых npm-зависимостей. Общий модуль `server/contact.mjs` использует Web Request/Response и может быть обёрнут другим сервером при будущем переезде.

Ответ успеха только после `Telegram sendMessage → ok:true`, затем записи статуса в D1: `{ok:true, accepted:true, requestId}`. Контракт проверяется клиентом. Код не объявляет бронирование подтверждённым. При ошибке значения сохраняются, mailto автоматически не запускается. Повторный клик блокируется до завершения. Повторный requestId не создаёт второе сообщение. При неопределённом результате сети автоматическая повторная доставка запрещена: оператору нужно сверить ID с тестовым/рабочим каналом.

Перед открытием формы клиент проверяет GET `/api/contact?country=vietnam`: без настроек/таблиц получает `{available:false}` и показывает прямые контакты. Проверка подтверждает наличие конфигурации, не доступность Telegram; это проверяется при POST. На статическом сервере без Functions будет честная ошибка, а не успешная отправка.

## Настроить только Preview

1. В существующем Cloudflare Pages проекте проверить, что staging разворачивается как Preview (Branch deployment controls), а production-ветка не изменяется. GitHub показывает два Pages проекта: vetratoria и vetratoria12; уточнить, какой является командным тестовым окружением.
2. В Preview задать `TELEGRAM_BOT_TOKEN`, `CONTACT_CHAT_VIETNAM` и `CONTACT_HASH_SECRET` как серверные secrets. Для теста использовать отдельный тестовый чат, не менеджеров. Для других направлений нужны отдельные `CONTACT_CHAT_DAHAB` и `CONTACT_CHAT_RUSSIA`; без них эти направления остаются недоступны для прямой отправки. Никакого fallback на другой чат.
3. Привязать отдельную тестовую D1 базу под именем `CONTACT_DB`, выполнить `server/contact-schema.sql` в этой базе. Не использовать production-базу. Здесь только хеши/статусы, без имён, телефонов, сообщений или сырых IP. Создание сервиса/платного плана этой задачей не выполнялось; использовать доступный тариф, платный не подключать без согласования.
4. Пересобрать Preview, проверить GET и один изолированный тест в тестовом канале. Проверить, что динамический `/api/contact` не возвращает статическую страницу. `_routes.json` ограничивает Functions одним API-маршрутом.
5. Секреты не передаются генератору как HTML-поля. `.env.example` — перечень без значений. Для локального Wrangler использовать игнорируемый `.dev.vars`, не помещать файл в артефакт публикации. При публикации корня репозитория сверить, что исходники/документы/.env файлы исключены из статической выдачи; предпочтительно настроить отдельную выходную директорию после согласования инфраструктуры. Не копировать secrets в root deployment.

## Endpoint и другой сервер

`CONTACT_ENDPOINT` — публичная build-переменная. По умолчанию `/api/contact`; можно указать HTTPS URL на отдельном API. Он должен реализовать тот же GET/POST-контракт. Для отдельного origin задать на сервере `CONTACT_ALLOWED_ORIGINS` списком точных origin через запятую. Не использовать `*`. Default разрешает только origin текущего сервера. При переносе на VPS оставить маршрут `/api/contact` через серверный адаптер или настроить endpoint; без него прямой приём работать не будет.

## Защита и ограничения

- Серверная проверка страны, дисциплины, формата контакта, размеров строк и JSON до 16 KiB; Origin allowlist; скрытое honeypot поле и минимальное время заполнения 2 сек.
- До 5 новых попыток за 10 минут на IP (только доверенный Cloudflare `CF-Connecting-IP`). Атомарные SQL-операции, блокировка ID/отпечатка перед запросом к Telegram. Хеши с серверным секретом.
- accepted/pending/uncertain сохраняются до 7 дней; истёкшие данные очищаются после успешной отправки. При отсутствии успешных отправок добавьте периодическую очистку на хостинге; она не настроена этой задачей.
- Блокировка точного повтора не заменяет очередь доставки. Если Telegram ответил успешно, а запись в БД упала, пользователь видит ошибку, повтор блокируется pending; оператор сверяет ID. Доставка сообщения не равна обработке менеджером.
- Массовый распределённый спам требует дополнительных мер платформы. CAPTCHA не подключалась, оплачиваемые сервисы не подключались.

## Аналитика

DOM events: `vetratoria:contact-open`, `vetratoria:contact-attempt`, `vetratoria:contact-success`, `vetratoria:contact-error`. Inline form также отдаёт open при первом фокусе. Detail содержит только country, sport, form; без имени, контакта, сообщения, query, UTM или yclid. Удалён старый contact-submit с персональными данными. При наличии внешнего обработчика обновить подписку. Существующих счётчиков в репозитории не обнаружено, ID не добавлялись.

UTM и yclid сохраняются в sessionStorage и передаются **только обработчику заявки**, отдельным объектом attribution. URL-источник передаётся без query/hash. Не привязывать конверсию к клику/attempt: цель подтверждённой заявки — только success. Не публиковать юридические тексты с вымышленными реквизитами; владельцу нужно подтвердить реальную политику и основание обработки перед production.

## Проверки без внешних сообщений

`node --test scripts/tests/contact.test.mjs` (Node 22.13+ с node:sqlite; проверено на Node 24). SQLite исполняет настоящий SQL, Telegram заменён локальной функцией. Тесты покрывают invalid/honeypot/origin, отсутствие конфигурации, успех/ошибку/timeout, дубли и конкурентную отправку, частоту, клиентский success-контракт, сохранение значений и отсутствие персональных данных в событиях. Это не проверка реальной доставки.
